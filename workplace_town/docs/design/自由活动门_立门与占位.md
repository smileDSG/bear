# 自由活动门：立门与占位

> 本文只写实现：门什么时候立、按什么分组、站在哪儿。玩法口径以《十二个月开发文档_V1.md》§4.15 为准。

## 1. 门是什么

`scripts/TownPortal.gd`（`Node2D`）画的一团程序化光效，零贴图。两个状态：

- `sealed = false`：金色，弧在转，粒子在飘。
- `sealed = true`：整扇压成石板灰，弧和粒子停住，走近只给「这个月还不能进」。

「已解锁 ≠ 能进」：解锁只负责把门立起来，能不能进由 `_month12_place_window_open()` 决定（剧情面板开着、过场锁着的时候一律进不去）。

## 2. 一扇门 = 一个区

门不是"某件事的入口"，是"这个区能进"。按 E 进的是区室内，进去之后右侧列**这个区所有能做的事**（`_enter_month12_place` → `_show_month12_place_list(zone_code)`）。所以：

- 同一个区无论挂几处去处，镇上只有一扇门（B 区：组内小工具 + 把活往前赶 → 一扇门、列表两行）。
- 后来解锁的活动只进 `_month12_unlocked_places`，不再多长一扇。

## 3. 数据结构

`data/story/v12m/activities.json` 每个去处：

```json
{
  "id": "m1_tool",
  "name": "组内小工具",
  "portal": { "zoneId": "B" },
  "unlockAfter": "E02",
  "apCost": 1
}
```

- `portal.zoneId`：先在哪个区的入口立门（取 `data/town/regions.json` 的 `entrance`）。
- `portal.landmark`：少数没有区的去处，坐标写死在 `_month12_place_position_of()`（`heart_lake` / `waterway` / `lawn`）。
- `unlockAfter` / `unlockHook`：二者至少一个，校验器第 26 条会把关。

运行时两张表：

| 表 | 键 | 值 | 含义 |
|---|---|---|---|
| `_month12_place_portals` | `activity_id` | `TownPortal` | **有门的那个活动**；一个区最多一条 |
| `_month12_unlocked_places` | `activity_id` | `true` | 所有已解锁去处（含共用同一扇门的） |

## 4. 接口

| 函数 | 作用 |
|---|---|
| `_ensure_month12_place(activity_id)` | 解锁一个去处：先记 unlocked，再看这个区的门是否已在，没有才建 |
| `_month12_place_door_key(activity)` | 门的分组键：`zone:B` / `landmark:lawn` / `activity:<id>` |
| `_month12_place_position_of(activity)` | 纯落点：`zoneId` 取区入口，`landmark` 查固定表 |
| `_month12_place_free_position(base)` | 兜底避让：同点已被别的门占着时左右 84 一档试六档，再上下 96 |
| `_month12_place_taken(point, occupied)` | 距离小于 72 像素判为占位 |
| `_month12_place_window_open()` | 现在能不能进门（面板没开、不在过场、处在可自由走动的相位） |
| `_update_month12_nearby_place()` | 选最近的一扇门，给「按 E 进去 · 活动名」 |
| `_begin_month_nodes_after_start_card(month, nodes)` | 月初卡"继续"后：第 1 月先弹心情讲解卡（`_hud_button_tutorial_config("mood")`），点"知道了"才 `_actually_start_month_nodes()`；讲解卡看一次就记 `mood` 已读，之后月份不再弹 |

## 5. 落点与兜底

1. 有 `zoneId` → 取该区 `entrance`，过 `_snap_month12_point()` 吸附到可走网格。
2. 有 `landmark` → 查固定坐标表（`heart_lake` 860,770 / `waterway` 1424,273 / `lawn` 640,900）。
3. 两者都没有 → 默认 (1008,240)。
4. 落点如果和**已存在的另一扇门**（不同门键）相距不到 72 像素，才走兜底偏移：`+84, -84, +168, -168, +252, -252`，再 `+96, +192, +288` 向下；全占满退回原点。
5. 每个候选点都重新吸附，偏移后不能落进湖里或墙里。

## 6. 判定与已知边界

- 「按 E 进哪一扇」是**最近优先**，不是先到先得（`_update_month12_nearby_place` 只在距离更近时替换）。
- 剧情那一眼的门（`_story_door`，第 2 月图书馆）不在门表里，不参与分组也不参与避让。
- 门是灰的也占位：玩家看得见"那儿有一个区，只是现在不能进"。
- 列表按 `unlocked` 过滤，不按"有没有门"过滤——共用门的第二个去处靠的就是这条。

# 自由活动卡：用新美术把"本区能做什么"铺成一列卡（2026-10-31）

> 素材到了 12 张，`assets/01_带缩略图面板/`。本文往上那几节讲"门"，这节讲"进了门看到什么"。玩法口径仍以开发册 §4.15 为准；这里只写这一层怎么落。

## 7.1 三层结构（沿用，不新增第四层）

1. **镇上一扇门 = 一个区**。见 §2，不动。
2. **进门 = 本区能做的事**。现在是纯文字行，改成**卡片列表**：一屏一列，每行一张横卡，可滚。
3. **点卡 = 到访确认页**。仍走 `PlaceVisitPanel.show_confirm()`，不新开一套确认。

卡片只负责"选哪件"，不承担结算。结算仍在活动结果页。

## 7.2 卡面：图只出零件，字一律现读数据（2026-10-31 改）

素材是整卡：`assets/01_带缩略图面板/<区>_<活动>_面板.png`，1200×340，区名、活动名、一句话、消耗数字全烙在像素里。

**不能直接把整卡贴上去**——烙的字和游戏的账对不上，逐条核过：

| 卡上烙的 | 游戏里实际 | 后果 |
|---|---|---|
| E 区两张印「财务部」、H 区两张印「生产部」 | E 是松风训练谷、H 是慢生活园（`ZONES`），A–D 才是部门名 | 玩家进门看到的区名和地图上那块牌子不是一套 |
| 「小馆咖啡聊天」 | 这条活动叫「销售部外摆」（`m3_waterway`） | 同一件事两个名字 |
| 「桌游馆」 | 叫「桌游角」（`m11_boardgame`） | 同上 |
| 每张都印「消耗 1」 | 有卡面的四条 `hCost` 全是 0；`m11_reproduce` 反倒是 2 | 卡上的数字是假的 |

（那套部门口径不是凭空来的：`assets/八大区域地图重制版/` 里 E–H 也叫 `E_财务部.png`…，但游戏实际用的是 `assets/场景内部图/松风训练谷.png` 那一组。图给的是旧口径。）

所以这一层只从图上取**不会错的两样零件**，其余照图的版式现画：

| 位置 | 内容 | 数据来源 |
|---|---|---|
| 左上胶囊 | 区名 | `_month12_zone_name(zone_code)`，读 `ZONES` |
| 左 | 缩略图 | `assets/ui/activity_cards/thumb_<区>_<活动>.png`（脚本切出来的） |
| 中 | 活动名 + 一句话 | `activity.name` / `_month12_place_row_note()` |
| 右 | 「消耗」+ 蜂蜜罐 + 数字 | `activity.hCost` |

**蜂蜜罐是心情，不是格子。** 全游戏蜂蜜罐只表示心情 H（HUD 顶上同款），所以右栏数字读 `hCost`。`hCost = 0` 时罐子压暗、写「不花」——实拍里写 0 会画成一个方框，而且"消耗 0"读着像坏数据。占几格走中间那行小字（`占 1 格 · …`），口径和右侧窄栏那条列表一致，由 `_month12_place_row_note()` 统一给。

零件由 `python tools/v12m_cut_activity_cards.py` 切，输出 `assets/ui/activity_cards/`。图重画了就重跑这个脚本，界面不用改。

## 7.3 数据结构

缩略图走 `thumbArt`：数据直接给切好的 395×190 图（`assets/ui/activity_cards/thumb_<区>_<活动>.png`），
`ActivityCardList._thumb_path()` 优先读它；没给才由 `cardKey` / `cardArt` 文件名推 key。

2026-11-11 起 `activities.json` 的 `cardArt` 按开发册 §4025 全删（此前 main_latest 还留着
`m5_umbrella` 一处）。为什么不只靠 `cardArt` 推 key：现在的整卡是小场景新UI 那套
980×330 / 1190×324 的烙字图，文件名是「02_上方活动卡」这种，推不出 `<区>_<活动>`，
硬推会得到一个不存在的 key、再 fallback 到整卡，票根左边就糊成一张被拉伸的整卡
（m5_umbrella 实拍过）。

```json
{
  "id": "m3_waterway",
  "name": "销售部外摆",
  "locationId": "C",
  "location": "C 区销售部外摆",
  "slots": 1,
  "hCost": 0,
  "thumbArt": "res://assets/ui/activity_cards/thumb_C_COFFEE.png",
  "card": { "title": "…", "lines": ["…", "…", "…"] }
}
```

- `thumbArt` 空 = 这条没缩略图，列表退化成**纯文字行**，不塌、不留白框。
- 兜底顺序：`thumbArt` → `cardKey` / `cardArt` 推 key 找切图 → 整卡 → 文字行，缺图不会开天窗。
- 12 条已全部配齐 `thumbArt`（2026-11-11），票根列表不再出现"一条整卡配十一条文字行"的混排。
- `card.lines` 是**解锁卡**的正文，不是票根卡的。两张卡分工见 §7.3.1。

## 7.4 接口

| 函数 | 变化 |
|---|---|
| `InteriorPreview.set_activities(activities, enabled, remaining)` | 先读 `activity.cardArt`，`ACTIVITY_CARDS` 表只兜底；每行按自己的 `disabled` 压灰；没整卡的走 `_draw_activity_ticket()` |
| `InteriorPreview._draw_activity_ticket(slot, dict, can_go)` | **新增**：同版式现画票根（牌子 / 名字 / 小字 / 消耗 + 蜂蜜罐），文字全读数据 |
| `ACTIVITY_SLOT_AT / _SIZE / _STEP` | **新增常量**：整卡和现画票根共用同一套格子坐标，两种卡不会错开 |
| `ActivityCardList.open(zone_title, items, points_text)` | `"page"` 那版（`scripts/v12m/ActivityCardList.gd`，CanvasLayer 150），面板高度跟内容走 |
| `_show_month12_place_list(zone_code)` | 组行时带 `badge` / `cost`；按 `MONTH12_CARD_SURFACE` 决定摆哪儿 |
| `_month12_zone_name(zone_code)` | **新增**：区名读 `ZONES`，票根左上那块牌子用它 |
| `_month12_place_plain_note(act)` | **新增**：只给"去那儿干什么"，不带代价前缀；`_month12_place_row_note()` 在它前面按需加「占 N 格 · 」 |
| `_begin_month12_activity(activity_id)` | 不变。卡片点击 → 同一个到访确认 |

`enabled` 判定顺序：活动没解锁 → 不再出现（列表已过滤）；心情 `H = 0` 且这条不缓心情 → 灰，理由「今天只能缓一缓」；`H = 0` 且这条能缓 → 留着能按，理由改写成「能缓过来一点 · 就按这个」。

## 7.5 卡的三态

| 态 | 画法 | 实装 |
|---|---|---|
| 可点 | 票根原样，整行是一张透明按钮 | ✅ |
| 不可点 | 整张压 55% 灰 + 左下一行理由，按钮 `disabled`，点不动 | ✅（理由来自 §7.4 的 `enabled` 判定） |
| 已完成 | 同不可点，理由写「这个月已经来过」 | ❌ 还没接：同月重复去现在仍按老路走，不压灰 |

### 7.13.1 两条毛病与修法（2026-10-31）

### 7.13.2 活动该加哪个属性（2026-10-31 修订，覆盖 7.13.1 里"补技能 +1"的说法）

**先纠正一个前提**：心情掉得少，不是因为活动给得少，是这本账本身天花板太低——H 上限 6、月初回满、一次最多扣 2，而且十个去处里七个 `hCost: 0`。全年实测最低只到过 5。想让"累"有意义，得先改这本账，不是往活动里塞更多扣钱项。

**能加的账，五本，按可行性排：**

| 账 | 现状 | 能不能用在活动上 | 代价 |
|---|---|---|---|
| **能力五格**（档案里那五排） | 现成，`abilityTags` → `_record_ability_tags`，还自带"长了一点 / 长进了一块"那句 | **能，首选** | 阈值 2/5/9：活动 +1 会加速到顶，得加一条"活动最多把某一格喂到第 3 格" |
| **档案材料** | 现成，材料栏已经在显示"留下的材料" | 能，最便宜的"看得见" | 只加已有两样之外的新条目要新旗标 |
| **关系档** | 算法册有 `relationships`，**客户端一行都没实现** | 要新建一本账（每个 NPC 一条档位）才能用 | 成本中等，且和"手机邀约"那套要打通 |
| **四维 S/O/N/D** | 现成 | **不建议** | 直接进 M6/M7/M12 判定，不该由"下班去玩"决定 |
| **心情 H** | 现成但天花板低 | 只作少数"硬扛型"活动的代价 | 想有效果得先抬账，见上 |

**结论**：活动给**能力五格 + 材料**，这两样玩家都看得见、也现成。关系档留给以后单独做——现在客户端连这本账都没有，挂上去也是空转。

## 7.15 自由活动是人格信号的主要来源之一（不是转正分）

先纠正一处口径：自由活动**确实**是评判大五人格的地方，而且《算法册》§3.1 早就写死了——B_t 的权重公式里有一项 `s_i`（来源类型）：**必玩 1.0 / 自由活动 0.5 / 自述 0.3**。也就是说活动进的是**人格信号轨**，权重是必玩的一半。

它不进的是**转正分**：算法册 §1「三轨不得换算」明确规定"活动奖励不能抬高 0–4 评分"，而转正只看主线选项产的证据条目。两条轨各走各的，互不折算。

**现在缺的不是设计，是落地三件：**

1. **活动埋点没人读**。每次到访已经在发 `mNN_activity`（`WorkplaceTown` 里 `record_event("m%02d_activity" …)`），但报告侧没有任何代码消费它。
2. **17 条活动都没标 B_t 信号**。每条活动至少要标：往哪个维度偏（x_i，−1..+1）、证据强弱（q_i）、情境相关度（r_i）、情境类型（独处 / 结伴 / 硬扛 / 帮人）。少了这些，活动那 0.5 的权重挂不上去。
3. **报告的"行为倾向观察"没接**。算法册 §3 的门槛是"3 个独立事件 + 2 类情境"，不够就写"观察不足"；现在报告根本没算这一段。

**信号怎么标（按活动性质粗分，具体逐条再定）：**

| 活动类型 | 例子 | 偏的维度 |
|---|---|---|
| 独处型 | 湖边散步、露台吹风、夜间值守 | 外向性偏低、内省 |
| 结伴型 | 团队密室、雨天共伞、文娱室合唱、夜间烧烤、桌游角 | 外向性、宜人性偏高 |
| 硬扛型 | 人事部长桌、复现论文、把活往前赶、松风训练谷 | 尽责性偏高；对局还带情绪稳定性 |

这样"活动丰富化"就有第二层意义：玩家常去哪儿，会变成年度报告里"你是个什么样的人"——**但不改变谁转正**。

### 好感度

- 四个人各一条档：**0–5**，对应档案上那五颗心；5 档以外另有"认可爪印"（表示他真拿你的东西用过，跟能力第 5 格呼应）。
- 增减来源：一起做完一次多人活动 **+1**；被邀请但对方没空 / 被拒绝（按剧情给的答复）**0 或 −1**；主线里替人挡事、署名让功这类事，接已有旗标给 **±1**。
- **不进转正判定**，不进能力五格；它是"这个人怎么看你"，只影响后续台词与可选做法。
- 回响：某人的档到 3 / 5 时，他身上某几屏多一句话或多一个做法；档掉到 1 以下，他会明显疏远。

### 手机邀请（多人活动专用）

触发：玩家在活动卡上选了 `mode: "multi"` 的活动、**还没走到地方**时，右下角手机自己亮一下，抽屉拉开一条：

> **要不要叫上谁？**
> · 小赵（这周在赶截图，应该有空）
> · 小林（最近在跟你核口径，未必想来）
> · 自己去

- 每条只给"他在忙什么"一句，不承诺一定来；点了就是发出邀请。
- 可以只叫一个，也可以两个都叫；**"自己去"永远留着**，不逼人社交。
- 到场后：来了的人在活动那一屏里出现、说一句话，结算给他 +1；没来的给一句"他回了句在忙"，不扣。
- 手机仍然不做自由输入——邀请是唯一"发出去"的东西（开发册既有口径）。

### 要定的

1. 现在只有 2 条多人活动，撑不起这套。是否把草坪、桌游，加上新卡里的密室 / 合唱 / 烧烤 / 共伞都标成 `multi`，各自写清能约谁。
2. 好感度够不够影响"他会不会来"——是纯剧情答复（看当期旗标），还是也看关系档。
3. 关系账放客户端还是后端：后端 `V12MState.relationships` 字段已经有了，客户端要读还是要自己记一本。

## 8.7 牌位避让：门隔得开，牌子会撞（2026-11-11 实拍追加）

### 现象

门与门之间本来就有避让（`_month12_place_free_position`：84 一档、判定半径 72）。
可判定半径按「门」算，牌宽却是 320 —— 两扇门各站各的，牌却叠上了。

实拍：第 5 月剧情门落在 F 区（世界 702, 833），旁边 E 区活动门在（848, 912），
横向只差 146。两块牌都挂门上方（`y = -150`），下面的 E 牌把 F 牌右下角压掉一块，
`audit_06` 那张图里「主厅那块大屏」右端只剩半截。

### 排布规则

`WorkplaceTown._layout_place_markers()`，每次有新牌出现就整屏重排一次：

1. 收集所有挂着 `_place_marker` 的门：`_month12_place_portals` 全部 + `_story_door` + `_sleep_portal`；
2. 全部复位成默认态（`set_marker_below(false)`、`set_marker_shift(0)`）；
3. 按**门的世界 y 升序**排（上面的门先占位，下面的门负责让）；
4. 逐块算牌的世界矩形＝门坐标 + `marker_offset_y()`，尺寸 320×88：
   - 与已占矩形不相交 → 就放这儿；
   - 相交 → 先往上抬一档（`PLACE_MARKER_STEP = 100`）；
   - 抬一档还相交 → 改挂门下方（`set_marker_below(true)`，`y = +58`）。

「改挂下方」是 `MARKER_ABOVE_MIN_Y` 那条规则的镜像：太靠上会顶进 HUD，抬不开就往门下方走。
牌挂在门下方时紧贴自己的门，指向不会含糊；`mouse_filter = IGNORE` 本来就不挡点击。

## 8.9 剧情月的门禁与「那一行」（2026-11-11 手机实拍）

### 三个叠在一起的 bug

玩家原话：「第二个月去人事部之后没有剧情，那个触发选项被删掉了，而且这个月没有
行动点，竟然可以在人事部选择自由活动」。

1. **门禁只看相位**：`_month12_place_window_open()` 只判 `phase in [month_nodes, activity]`。
   偶数月（2/4/6/8/10/12）在 `manifest.apByMonth` 里没有额度（AP=0），可相位照样是
   `month_nodes`，于是每扇门都是金的，玩家能拐进任何一处做自由活动。
2. **「那一行」被整卡漏掉**：`_show_month12_place_list` 先拼 `rows`（第一行是这一趟要去的
   `peek` 行），再按 `has_activity_card()` 过滤成 `carded` 走整卡叠。`peek` 行没有整卡，
   一过滤就没了 —— 第 2 月人事部屋里只剩一张「书院露台吹风」，玩家找不到翻旧单的入口。
3. **压灰判断带前提**：`lacks_ap` 前面顶着 `_month12_activity_generic and phase == "activity"`。
   剧情月 `generic` 是 false，这条判断整条失效，AP=0 也照样能点。

### 改法

```gdscript
# 1) 门禁：这个月没有行动点额度，门就不给进（黄线终点那扇由封条逻辑单独保亮）
if _ap_total <= 0:
    return false

# 2) 有 peek 行就不走整卡叠（叠里只装得下整卡，会把它漏掉）
var has_visit_row := not visit.is_empty() and String(visit.get("locationId", "")) == zone_code

# 3) 压灰只看有没有点，不再看是哪种月份
var lacks_ap := _month12_ap_left < int(act.get("apCost", 1))
```

### 数据结构

| 字段 | 来源 | 说明 |
| --- | --- | --- |
| `_ap_total` | `manifest.apByMonth[month]`（只有 1/3/5/7/9/11 有值） | 「这个月有没有自由安排」的唯一判据 |
| `has_visit_row` | `_month12_visit_place().locationId == zone_code` | 这一趟要去的行在不在 |
| `row.apCost` | `activities.json.apCost` | 压灰比较用 |

### 验收

`tools/m2_probe.tscn`（第 2 月、AP=0、D 区）：

```
[M2] 进 D 区屋里｜面板可见=true｜行数=2
     行：要去的 · 人事部二楼 · 旧档案架 / 翻旧事故单   可点=true
     行：书院露台吹风 / 行动力不足 · 需要 1 点        可点=false
```

- 剧情那一行在，可点；
- 旧活动在，但压灰并写明「行动力不足 · 需要 1 点」；
- 第 2 月地图上的门全灰（`_ap_total = 0`），只有黄线终点那扇保亮；
- 首月链路未被破坏：`p8_flow_guide_probe` 仍 PASS。

### 附带修的一处数据

## 8.9.1 剧情段的门禁：所有自由活动门压灰（2026-11-11 真机，P15）

### 现象与口径

玩家原话：「还有第三个月开始应该是什么都去不了的，所有门都要变灰」。
第 2 月因为 `_ap_total = 0` 已经在 §8.9 全灰，但第 3/5/7/9/11 月有行动点额度，
`_month12_place_window_open()` 又把 `month_nodes`（走主线剧情）算作可进门的相位，
于是玩家一路推剧情，旁边的门全是金的，随手就能拐进去做自由活动。

用户拍板的口径是 **剧情段全灰，窗口再亮**：走主线剧情时地图上没有一扇能进的自由活动门；
走到本月 `M03_ACTIVITY`（`activity` 相位）那一拍，门一起亮回来。
**不改 `apByMonth`、不取消任何月份的自由活动、不改三册**——「剧情段不能去」和
「这个月有没有额度」是两件事，前者归相位，后者归账。

### 判定链

| 相位 | 改前 | 改后 |
|---|---|---|
| `month_nodes`（主线剧情推进 / 剧情那一眼） | `runner_month` 返回 `true` → 门金、E 亮 | `false` → 自由活动门全灰、E 不亮 |
| `activity`（本月自由安排） | `true` | `true`（不变） |
| 偶数月任意相位 | `_ap_total <= 0` → `false` | `false`（§8.9 不变） |
| 剧情面板打开 / 过场锁 | `false` | `false`（不变） |

E 提示与进门共用 `_month12_place_window_open()`，一刀切会把剧情目标门也封死。
故 `_update_month12_place_prompt()` 拆成两个独立开关：

```gdscript
var free_window := _month12_place_window_open()
var story_visit := not _month12_visit_id.is_empty() and _month12_phase == "month_nodes"
if not free_window and not story_visit:
    _interaction_button.hide()
    return
# free_window 为真才遍历 _month12_place_portals；story_visit 为真才认 _story_door
```

### 数据结构（不新增存档字段、不改 JSON）

| 字段 / 常量 | 类型 | 来源 | 用途 |
|---|---|---|---|
| `_month12_phase` | `String` | 月份播放器 | 门禁唯一相位判据，改后只认 `activity` |
| `_ap_total` | `int` | `manifest.apByMonth[month]` | 偶数月 0 → 整月全灰（§8.9 既有规则） |
| `_month12_visit_id` | `String` | `_arm_month12_place_visit()` | 非空 = 当前这一屏是「去看一眼」，剧情门放行 |
| `_story_door` | `TownPortal` | `_open_story_door()` | 不在 `_month12_place_portals` 里，不参与压灰遍历 |
| `_month12_open_zones` | `Dictionary` | `_open_month12_zone()` | 门是否属于已开放区（§8.9 的附加守卫） |
| `PLACE_STORY_KEEP_OPEN` | `const float = 150.0` | `WorkplaceTown.gd` | 黄线终点附近那扇保亮，不跟着压灰 |
| `MONTH1_E02_PLACES` | `const Array = ["m1_tool","m1_lakeside"]` | `WorkplaceTown.gd` | 首月 E02 解锁白名单，与可去清单共用一张表 |

### 接口

| 接口 | 变化 | 作用 |
|---|---|---|
| `_month12_place_window_open() -> bool` | 改 | 去掉 `month_nodes` 与 `runner_month` 分支，统一 `return String(_month12_phase) == "activity"` |
| `_update_month12_place_prompt()` | 改 | 新增 `free_window` / `story_visit`；活动门遍历包进 `if free_window`，剧情门条件加 `story_visit` |
| `_refresh_month12_place_seals()` | 不变 | `open_now = false` 时把所有门表里的门 `set_sealed(true)`；`story_points` 保亮黄线终点 |
| `_open_month12_places(after_event, allowed_ids)` | 改 | 新增可选白名单。首月传 `MONTH1_E02_PLACES`，避免 `m1_rooftop`（D 人事部）被「解锁即开区」带回 |
| `tools/m3_gate_probe.tscn` | 新增 | 三态探针 + 真渲染出图，见下 |

### 例外（「所有门都灰」不成立的一处，主线必需）

- **剧情「去看一眼」那扇**：`_story_door` 独立立门、不走门表，且 `_arm_month12_place_visit()`
  把相位设成 `month_nodes`。它靠 `story_visit` 单独放行，否则第 2 月人事部、第 5 月运营部
  这些主线节点会直接卡在门口。万一它复用了某扇活动门（`_story_door_reused`），
  `_refresh_month12_place_seals()` 也只给这一扇留 `set_sealed(false)`。
- **黄线终点不再保亮**：2026-11-11 全年巡检发现旧 `story_points` 保亮会造成「门金着、E 却不出现」，
  已整段撤除，详见 §8.9.2。

### 验收（`tools/m3_gate_probe.tscn`）

## 8.10 真机回归：活动数据的两条契约（2026-11-11）

真机包的工作树是 `workplace_town_main_latest/`（本仓是文档/设计口径）。出图复核时一次抓到两处数据被洗平：

### 数据结构

| 字段 | 类型 | 口径 |
|---|---|---|

| `InteriorPreview.ACTIVITY_CARDS[id]` | `String` | 屋里那叠的**整卡**（小场景新UI 那套烙字图）；`activities[].cardArt` 已于 2026-11-11 按开发册 §4025 全删 |
| `activities[].hCost` | `int ≥ 0` | 额外扣的心情 H；`H≤2` 时翻倍（行动点不翻） |
| `activities[].stateDelta.H` | `int` | 活动本身给回的心情；回心去处写 `1` |

心情取值仍以 §4.25 / 算法册 §7.3 为准：回心 5 条（`m1_rooftop`、`m1_lakeside`、`m3_waterway`、

## 8.11 已解锁 = 可进入：第 7 月别按区二次拦截（2026-11-11 真机）

真机反馈「第 7 月只有熊熊有招和草坪运动」，用户拍板口径：**凡是已经解锁的活动，当月都要能选**。
`M07_FREE.activityIds` 本来就写了 9 条（旧 6 条 + `m7_valley` / `m7_lawn` / `m_grind`），
`budget.ap=3 / slots=1`；少掉的 7 条不是数据漏配，是被「区是否开放」筛掉的。

### 根因：两本账 + 四处按区拦截

`_month12_unlocked_places`（活动解锁）和 `_month12_open_zones`（区开放）各写各的。续玩 / 跳月的兜底里
E 区要 `month >= 8` 才自动开（第 7 月只有真走到 `M07_SPORTS_INVITE` 那一屏才开 E）。存档只恢复
`unlockedPlaces`、`openZones` 没恢复全时，已解锁活动会在下面四处被挡：

| 位置 | 原来的拦法 |
|---|---|
| `_unlock_month12_place()` | `_is_month12_zone_open()` 前置判断，区没开直接不立门 |
| `_ensure_month12_place()` | 开头 `not _month12_open_zones.get(locationId) → return`，连解锁账都不写 |
| `_available_month12_activity_ids()` | `zone ∈ C–H` 白名单 + `not _month12_open_zones.get(zone)` 两道筛 |
| `_refresh_month12_place_seals()` | `want_sealed` 里再叠加一次 `not _month12_open_zones.get(...)` |

### 数据结构（运行时状态，不新增 JSON 字段）

| 状态 | 类型 | 写入约束 |
|---|---|---|
| `_month12_unlocked_places` | `Dictionary[String, bool]` | 只在 `_ensure_month12_place()` 里写 `true` |
| `_month12_open_zones` | `Dictionary[String, bool]` | 解锁活动时由 `_ensure_month12_place()` 顺手补写所在区；剧情节点仍可提前开区 |
| `_month12_places_open` | `bool` | 补开 C–H 区时一并置 `true` |

**不变式**：`_month12_unlocked_places[id] == true` ⇒
`_month12_open_zones[activities[id].locationId] == true`。写解锁账的地方只有一处，两本账不会再对不上。

### 接口

| 函数 | 改动 |
|---|---|
| `_ensure_month12_place(activity_id)` | 解锁时先补开所在区（只写状态、不调 `_open_month12_zone()`，避免顺手给未解锁活动立区门），再写解锁账 |
| `_unlock_month12_place(activity_id)` | 去掉 `_is_month12_zone_open()` 前置拦截 |
| `_available_month12_activity_ids(ids) -> Array[String]` | 候选只认 `_month12_unlocked_places`；保留 `visited` / `apCost > ap_left` / `slots > slots_left` 三条本月预算过滤 |
| `_refresh_month12_place_seals()` | `want_sealed` 只看 `_month12_place_window_open()`；黄线终点那扇门保亮不再要求区已开 |

**刻意不改**：偶数月 / 剧情月没额度时的门压灰（`_month12_place_window_open()`）、到访制按区列室内活动
