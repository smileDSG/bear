## 关键决策

**根因（两条状态账对不上）**

- 活动解锁写 `_month12_unlocked_places`，区开放写 `_month12_open_zones`，是两本独立的账。
- `_ensure_month12_place()` 开头就是 `not _month12_open_zones.get(locationId) → return`，`_unlock_month12_place()` 外层还有 `_is_month12_zone_open()` 再拦一次；`_available_month12_activity_ids()` 又拿 `zone ∈ C–H` 白名单和 `not _month12_open_zones.get(zone)` 各筛一次；`_refresh_month12_place_seals()` 也按区压灰。
- 续玩 / 跳月的兜底里，E 区是 `month >= 8` 才自动开（`WorkplaceTown.gd:4265`、`:6797`），第 7 月只有真走到 `M07_SPORTS_INVITE` 那一屏才 `_open_month12_zone("E")`。存档若只恢复了 `unlockedPlaces` 而 `openZones` 不全，两套账立刻错位：已解锁的旧活动全部被区状态筛掉 / 门压灰，玩家眼里只剩当月刚解锁的 E 区两条。
- 数据本身没问题：`M07_FREE.activityIds` 明写 9 条（旧 6 条 + `m7_valley` 熊熊有招、`m7_lawn` 草坪运动、`m_grind` 文娱室合唱），`budget.ap=3 / slots=1`。`activities.json` 每条都写了 `gatedBy: month_required`，但全代码没有消费者；开发册 §4.5 说的「当月必玩主线没做完贴封条」实际是靠 `_month12_open_zones` + 相位算的，登记为后续独立口径项，本期不动。

**口径与改动边界**

- **已解锁 = 可进入**：解锁某处活动时，顺手把它所在的区标为已开放，两本账永远一起写；候选与门压灰不再拿区状态二次拦截已解锁活动。
- **不改**：偶数月无行动点时的门压灰（`_month12_place_window_open()`）、到访制按区列室内活动（`_show_month12_place_list`）、本月预算过滤（`visited` / `apCost > ap_left` / `slots > slots_left`）、「剧情必须走到才开」的解锁时机。
- 不改三册、不改 `activities.json` / `events.json` 的字段与数值；这是运行时状态修复，不是数据契约变更。
- 改动落 `workplace_town_main_latest`（真机包对应的 worktree），任务 / 设计文档仍写在本仓 `docs/`，与昨天真机验收任务一致。

## 全年复查（2026-11-11 追加，用户问「其他月份有没有这个问题」）

新增 `tools/all_month_unlocked_probe.gd` / `.tscn`：把每个自由活动月的 `openZones` 摆成续玩 / 跳月兜底的最坏状态（剧情提前开的区会丢），逐月比对改动前后，并验门压灰。结果 `[ALL-MONTH] PASS`：

| 月 | 节点 | 改前 → 改后 | 改前掉的活动 |
|---|---|---|---|
| 1 | `M01_ACTIVITY` | 0/3* → 3/3 | 首月三条*（通用路径模拟值，首月实际不走这套） |
| 3 | `M03_ACTIVITY` | 4/4 → 4/4 | 无 |
| 5 | `M05_FREE` | **4/6 → 6/6** | `m5_stage`、`m5_umbrella`（F 区，`M05_DAWN` 剧情开的，兜底第 6 月才开） |
| 7 | `M07_FREE` | **7/9 → 9/9** | `m7_valley`、`m7_lawn`（E 区，兜底第 8 月才开） |
| 9 | `M09_FREE` | 9/9 → 9/9 | 无 |
| 11 | `M11_FREE` | **10/11 → 11/11** | `m11_boardgame`（H 区，`M11_OPEN` 剧情开的，兜底第 12 月才开） |

**结论**：同一根因在 **第 5 / 7 / 11 月**都会发作，规律是「剧情提前开的区」早于「续玩兜底开区的月份」；H 区最极端。第 3 / 9 月不受影响。改动后六个月全部满分、门全亮。

**登记但不改**（需按三册口径单独拍板）：① `M07_FREE` 是全年唯一 `ap=3 / slots=1`，做完 1 点活动后 slots 归零、剩余 8 条被预算筛掉，剩 2 点行动力没处花；② `m7_valley`（3 点）只在 M07 的 `activityIds`，第 9/11 月 `ap=1` 必然筛掉它，等于第 8 月起永不出现；③ `gatedBy: month_required` 无消费者。

**仓库分叉**：`workplace_town_main_worktree/` 仍带旧的按区拦截（从它打包会复发）；`workplace_town/` 与 `workplace_town_sjl_build/` 是更旧版本、本来就没按区拦截。本期只改真机包对应的 `workplace_town_main_latest/`，是否同步旧 worktree 等用户拍板。
